Les canaux — AD-3 · AD-14

Trois canaux, trois usages

SSH — agir

Le canal historique : update, restart, backup à la demande, logs, healthz de diagnostic. Identité par machine depuis fleet.yaml, partout.

HTTP tailnet — observer

Nouveau : Homeport sert événements, métriques et capabilities sur son serveur web existant. Le tailnet est l'authentification ; une seule exception ATS, partagée URLSession + WebView.

scp — consolider

Les archives de backup produites sur le Pi sont rapatriées au fil des refreshs (rotation 10 côté Mac), en single-flight par machine.

Dégradation partout : trois états affichés distinctement — disponible non disponible (API absente) injoignable

Le contrat inter-repos — AD-4

Un contrat d'API, un seul rédacteur

  • Source de vérité dans le repo Homeport (c'est lui qui implémente le serveur) ; copie épinglée docs/api/ côté HomePortManager.
  • Versionné semver ; GET /api/capabilities renvoie version, features servies et epoch d'historique ; hpm déclare la plage qu'il consomme.
  • Le story-spec de la story 6 rédige seul la v1 complète (capabilities + events + metrics) ; la story 7 la consomme sans l'étendre.
  • API absente ou hors plage = affichage dégradé, jamais une erreur.

Les backups planifiés — AD-9 → AD-11 · AD-16

Le Pi travaille, le Mac orchestre

Sur le Pi

homeport-backup.timer déployé par hpm ; script root et autonome : data dir résolu localement, mqtt.env inclus, backup Homeport natif si disponible sinon générique, archives atomiques (tmp + mv), rotation 3. Tourne Mac éteint.

Sur le Mac

La définition des jobs (planning, rétention) vit dans la config hpm, appliquée de façon idempotente. Consolidation au refresh + hpm backup sync. Précondition sudo vérifiée par doctor avant tout déploiement.

Les exécutions du timer se racontent en événements — le journal Mac ne consigne que ce que le Mac initie (AD-16).

La concurrence — AD-12 · AD-17

Une mutation à la fois, verrous des deux côtés

Entre process Mac

CLI et app = deux process : le verrou par machine est persistant dans hpm.db, pas une file en RAM. Il porte son détenteur (PID + horodatage) et se reprend seul s'il est périmé — process mort ou TTL 30 min.

Entre Mac et Pi

flock partagé côté Pi : le timer saute son tour si une action hpm est en cours, et inversement. Jamais un backup pendant un update.

Le shell : évasion assumée

Pas de verrou, pas de journal détaillé — même statut qu'un SSH manuel. Identité fleet.yaml obligatoire, une entrée informative à l'ouverture.

Les lectures (status, logs, métriques, événements) restent libres et parallèles.

Différés — avec conditions de reprise

Ce qu'on ne décide pas aujourd'hui

  • Console web — quand le natif est livré. AD-3 et AD-14 lui préparent un seul point HTTP à durcir.
  • Token applicatif + HTTPS tailscale cert — si la flotte sort du tailnet personnel, ou avec la console web.
  • Stream SSE/WebSocket — optimisation de confort ; le pull à curseur reste la vérité.
  • SwiftTerm 2.0, swift-argument-parser 1.8+ — avec la montée de toolchain Swift 6.
  • Sparkle — backlog, hors spec.
